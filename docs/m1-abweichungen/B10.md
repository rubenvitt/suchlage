# Abweichungen Task B10

Abweichungen vom Plan `docs/superpowers/plans/2026-10-16-m1-live-lage.md`, Task B10.
Die Schnittstellen aus dem Plan sind unverändert:

- `settings::{Settings, OidcSettings, DjiSettings, BrokerSettings, SettingsHandle}`, `redirect_url`, `validate_oidc`
- `auth::setup::{ensure_token, consume, required}`, `auth::dev::seed`
- die Routen `GET /api/settings`, `PUT /api/settings/{section}` und `POST /api/setup`
- `AppState.settings`

## Einmal-Link wird in einem Schritt verbraucht

Im Plan las `consume` den Token, prüfte ihn und löschte ihn dann mit einem eigenen
`sqlx::query("DELETE …")` in `auth/setup.rs`. Das hatte zwei Haken:

- `auth` schrieb SQL selbst, obwohl laut Bausteintabelle nur `store` sqlx-Abfragen stellt.
- Zwei gleichzeitige Anfragen mit demselben Token kamen beide durch die Prüfung. Damit war der
  Link nicht wirklich einmalig.

Jetzt gibt es `store::settings::delete_if(pool, key, &expected) -> bool`. Die Funktion löscht den
Schlüssel nur, wenn er noch genau den gelesenen Wert trägt, und meldet, ob diese Anfrage gelöscht
hat. `consume` prüft Ablauf und Hash wie im Plan und verbraucht den Token danach mit `delete_if`.
Bei 0 Zeilen lehnt `consume` ab. Ein falscher Token löscht nichts, eine anonyme Anfrage kann den Link
des Admins also nicht entwerten.

## Prüfregeln stehen einmal

`validate_oidc` wiederholte im Plan die Regeln aus `update_oidc`. Beide nutzen jetzt dieselbe reine
Funktion `oidc_value(input, stored)`. `validate_oidc` ruft sie ohne gespeichertes Geheimnis auf, so
wie es in der Ersteinrichtung ist. Damit können die Regeln für Einrichtung und Einstellungen nicht
mehr auseinanderlaufen.

## Adressen brauchen einen Rechner

Im Plan prüfte `with_scheme` nur den Anfang. `tcp://` allein oder `http://` ohne Rechner wäre
durchgegangen. `address(v, schemes, field)` liest die Eingabe jetzt mit `url::Url::parse` und
verlangt ein erlaubtes Schema und einen nicht leeren Rechner. Gespeichert wird weiter die Eingabe
ohne Rand und ohne `/` am Ende. Die normalisierte Form von `url` bleibt außen vor, denn sie hängt bei
http(s) ein `/` an. Die Meldung lautet „<Feld> muss mit tcp:// beginnen und einen Rechner nennen“.

`issuer_allowed` lässt `http` jetzt auch für die IPv6-Loopback-Adresse `[::1]` zu, nicht nur für
`localhost` und `127.0.0.0/8`.

## Kein auskommentierter Platzhalter für B11

Der Plan setzte in `setup` die Zeile `// B11 ergänzt hier: state.oidc.check_discovery(…)` ein. Das
ist auskommentierter Code, deshalb fehlt die Zeile. B11 fügt die Discovery-Prüfung an derselben
Stelle ein: nach `validate_oidc` und vor `consume`.

## Test-Modul von `auth::setup` nur ohne Feature `dev`

Im Plan stand `#[cfg(not(feature = "dev"))]` nur am Test. Mit `--features dev` wäre `use super::*;`
dann unbenutzt gewesen, und `cargo clippy --all-targets --features dev -- -D warnings` hätte das Gate
gebrochen. Mit Feature `dev` ist nie eine Einrichtung nötig. Deshalb gilt
`#[cfg(all(test, not(feature = "dev")))]` jetzt für das ganze Modul.

## Kleinere Abweichungen

- Die private Speichermethode von `SettingsHandle` heißt `save` statt `store`. Sonst hätte sie
  denselben Namen wie das Modul `store`, das in denselben Methoden vorkommt.
- `settings/mod.rs` und `auth/dev.rs` importieren die Vertragstypen einzeln statt über
  `crate::contract::*`.
- Fehler beim Start (Seed, Einrichtungslink) gibt `run` als `{e:?}` weiter, über `startup_error`.
  `Display` zeigt bei `AppError::Internal` nur „Interner Serverfehler“, und ein DB-Fehler beim Start
  wäre so nicht nachvollziehbar.
- Wie die Lage den Einstellungen folgt, steht in einer eigenen Funktion `app::follow_settings` statt
  in einem Block in `run`. `run` abonniert die Einstellungen, bevor es den Startwert für `Config`
  liest. So geht keine Änderung zwischen Startwert und Nachführen verloren. Gelesen wird mit
  `borrow_and_update`.
- Die Routentests verwenden den gemeinsamen Helfer `testing::put_json` neben `post_json`. Der Plan
  hatte dafür eine eigene Funktion `put` im Testmodul.
- Commit-Pfade: Neben den Pfaden des Plans kommen `src/store/settings.rs` (`delete_if`) und diese
  Datei dazu.

## Zusätzliche Tests

- `settings::addresses_need_scheme_and_host`:
  - `tcp://` allein, eine Adresse ohne `//` oder ohne Schema und eine leere Eingabe werden
    abgelehnt.
  - Für den Issuer gilt Loopback (v4, v6, `localhost`) mit http, eine private Adresse nicht.
  - Eine UUID ohne Bindestriche ist keine Workspace-ID.
- `settings::setup_input_is_validated_without_a_stored_secret`: Ohne Geheimnis, mit leerem Geheimnis
  und mit einem Issuer ohne Schema schlägt `validate_oidc` fehl.
- Die Plan-Tests prüfen zusätzlich:
  - Ein Geheimnis aus Leerzeichen behält das gespeicherte.
  - `has_client_secret` steht in der Sicht.
  - Ein abgelehnter Wert wird nicht gespeichert.
  - Port 0 und eine Media-Adresse mit falschem Schema werden abgelehnt.
  - Die Media-Adresse überlebt das Neuladen ohne `/` am Ende.
- `store::settings::delete_if_removes_only_the_expected_value_once`: Ein anderer Wert löscht
  nichts, der richtige löscht genau einmal.
- `auth::setup::wrong_token_does_not_burn_the_link`: Nach einem falschen Token gilt der richtige
  weiter.
- `auth::setup::no_link_once_oidc_or_an_account_exists`: Mit OIDC-Einstellungen gibt es keinen
  Link, mit einem Konto ebenfalls nicht.
- `web::auth::setup_link_configures_oidc_exactly_once` (ohne Feature `dev`):
  - `options` meldet vorher `setup_required: true` und die Callback-URL aus der öffentlichen Adresse.
  - Ein falscher Token ergibt 401.
  - Ein Tippfehler im Issuer ergibt 400, der Link bleibt gültig.
  - Danach richtet derselbe Link OIDC ein (Issuer ohne `/`, Geheimnis gespeichert).
  - Danach meldet `options` `oidc: true` und `setup_required: false`.
  - Ein zweiter Aufruf ergibt 409 und ändert nichts.
- `web::admin::settings_need_a_session`: ohne Sitzung 401.
- Die Admin-Tests prüfen zusätzlich:
  - `GET /api/settings` als Operator ergibt 403.
  - Das Passwort steht nirgends in der Antwort.
  - Ein fehlendes Feld bei `general` ergibt 400 mit „Ungültige Anfrage: …“.
- `auth::dev::seed_fills_only_what_is_missing` (nur Feature `dev`):
  - Ein vorher gesetzter Broker bleibt.
  - Media und DJI werden ergänzt, OIDC nicht.
  - Ein leerer Stand bekommt die Dev-Werte für den Broker.

Für `follow_settings` gibt es keinen Unit-Test. Ein solcher Test liefe gegen einen eigenen Task um die
Wette, und eine Konfiguration der Lage ist von außen nicht lesbar. Offen: Ob der Aktor die
Einstellung übernimmt (Startwert und spätere Änderung), belegt bisher weder ein Test noch der Lauf
des Binarys. Ohne MQTT-Eingang (B12) startet dort kein Flug. Sichtbar wird es mit dem Auto-Start in
B13 und im Dev-Smoke von I1. Der Lauf des Binarys belegt nur Seed und Einrichtungslink (siehe unten).
