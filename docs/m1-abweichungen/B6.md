## sqlx 0.9 nimmt nur geprüfte SQL-Strings an

`sqlx::query` erwartet in 0.9 ein `impl SqlSafeStr`. Das erfüllen nur `&'static str` und Werte in
`AssertSqlSafe`. Der Plan-Code `sqlx::query(&format!("SELECT {COLUMNS} …"))` kompiliert deshalb nicht
(sieben Stellen in `flights.rs` und `remote_controllers.rs`).

Statt jeden String mit `AssertSqlSafe` freizugeben, steht die Spaltenliste jetzt in einem kleinen
`macro_rules!`. Die Abfragen entstehen mit `concat!` und bleiben `&'static str`:

- `flights.rs`: `select_flights!("WHERE id = ?")`
- `remote_controllers.rs`: `concat!("SELECT ", columns!(), " FROM …")`

So prüft der Compiler, dass keine Laufzeitwerte ins SQL geraten. Die Spaltenliste gibt es trotzdem
nur einmal. Die Konstante `COLUMNS` entfällt.

## SQLITE_BUSY auch mit erweitertem Code erkennen

sqlx-sqlite liefert in `DatabaseError::code()` den erweiterten Ergebniscode
(`sqlite3_extended_errcode`). Der Plan verglich nur mit `"5"` und `"6"`. Damit wären
`SQLITE_BUSY_SNAPSHOT` (517), `BUSY_RECOVERY` (261), `BUSY_TIMEOUT` (773) und `LOCKED_SHAREDCACHE` (262)
als „Interner Serverfehler“ angekommen. 517 ist im WAL-Betrieb realistisch, zum Beispiel wenn
`upsert_oidc` in einer verzögerten Transaktion erst liest und dann schreibt.

Der Helfer `is_busy_or_locked` liest den Code als Zahl und prüft das untere Byte (den primären Code)
auf 5 oder 6.

## Gerätestand: unlesbare Einträge werden gemeldet

`settings::get` meldet einen unlesbaren Wert mit `tracing::warn!`. `device_state::all` hat im Plan
einen unlesbaren Eintrag still verworfen. Jetzt warnt es ebenfalls, mit der SN des Geräts. Das
Verhalten bleibt gleich: Der Eintrag fällt weg, die übrigen Geräte kommen zurück.

  `view` enthält keine Zugangsdaten.
